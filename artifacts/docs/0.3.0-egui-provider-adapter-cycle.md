## 0.2.9 Intel provider behavior

Intel normal user-facing paths use visible-sample priming so interval-derived counters have a prior sample before the first user-visible tick:

```text
wtg.exe --once --provider intel
wtg.exe --watch --provider intel
wtg.exe --once --stats --provider intel
wtg.exe --watch --stats --provider intel
```

Raw diagnostic probe remains raw and may report first-sample unavailable states:

```text
wtg.exe --probe --provider intel
```

Expected distinction:

- user-facing once/watch/stats paths: primed visible sample
- probe path: raw diagnostic behavior

Intel human/UI wording rule:

- Do not render `delta` in human/UI labels.
- Render as:
  - `Power: X W`
  - `Engine N: X%`
- Provider-native stats/schema field names may remain explicit, including names such as `watts_delta` and `utilization_pct_delta`.

## eGUI implementation notes

Current spike implementation is provider-backed, not a separate telemetry workflow.

`wtg-app/src/ui.rs` imports existing providers:

```rust
use wtg_providers::{amd_adl, intel_level_zero};
```

Refresh path collects:

- NVML snapshots through existing `wtg_core::nvml` path.
- AMD views through `amd_adl::collect_once` plus provider stats JSON formatting/parsing.
- Intel views through `intel_level_zero::collect_visible_sample` plus provider stats JSON formatting/parsing.

This JSON-to-view-model path is acceptable for the spike. A later cleanup may replace it with typed provider view structs.

## Gauge behavior

Preserve the existing eGUI gauge style where values are real.

NVIDIA:

- GPU utilization gauge
- Memory-controller utilization gauge
- VRAM used/total gauge

AMD:

- Activity gauge only when `activity_pct` is available.
- No fake memory gauge when memory info is unavailable.

Intel:

- Engine utilization gauges when values are available.
- Memory used/total gauge when values are available.
- Do not append `delta` to engine labels.

General rule:

- Do not render unavailable values as `0%`.
- Do not synthesize cross-vendor parity fields.

## Artifact handoff lesson

`wtg-ui.exe` alone is not a complete test/release handoff for MQTT UI workflows.

The eGUI MQTT actions shell out to `wtg.exe`. Test/release folders must include both executables side by side:

```text
wtg-ui.exe
wtg.exe
```

Observed failure when only `wtg-ui.exe` was copied:

```text
CLI launch error: program not found
```

Immediate fix:

- Copy the matching `wtg.exe` into the same folder as `wtg-ui.exe`.

Future eGUI fix:

- First look for `wtg.exe` beside the running `wtg-ui.exe`.
- Optionally fall back to `PATH`.
- If missing, show an explicit error such as:

```text
wtg.exe not found next to wtg-ui.exe
```

rather than the generic:

```text
CLI launch error: program not found
```

## MQTT / Home Assistant redline issue

The redline/unavailable issue is not caused by the new 0.3.0 eGUI provider adapter work.

Evidence:

- New 0.3.0 eGUI showed Home Assistant entities as unavailable/redline.
- Old beta6 `wtg-ui.exe` showed the same Home Assistant status with the same config.
- Therefore the new eGUI adapter spike is not the root cause.

Observed Home Assistant behavior:

- Diagnostic entities such as Driver, CUDA driver, Compute mode, PCI bus, Performance state, and WTG version showed `Unavailable`.
- History showed valid values briefly, including values such as `P8` and `0.3.0`, then current state returned to `Unavailable`.

Likely class of issue:

- MQTT/Home Assistant availability behavior.
- Retained discovery or retained availability/LWT issue.
- State-topic mismatch.
- Publisher lifecycle/disconnect behavior.
- Old retained NVIDIA-only diagnostic entities stranded by later schema/provider changes.

Do not block 0.3.0 eGUI provider adapter work on this.

Treat it as a later redline cleanup cycle when MQTT/Home Assistant integration is revisited for expanded providers.
